# Scan and removal behavior

## Review and removal

- Expand an app to inspect the bundle and every matched path, size, category, and match reason. Show in Finder resolves the current scan-item ID in main.
- Review removal separates the bundle, caches/logs, and settings/local data. Only the bundle is selected initially; data starts unchecked. A second screen lists every selected path and its estimated size before **Confirm move to Trash**.
- Possible leftovers require explicit selection and confirmation. Unmatched ownership does not establish that files are unused. Generic names are uncertain and protected. The Selectable only filter hides protected and incomplete leftovers plus the protected shared/related lists; it does not change the scan-wide summary or current selection. Shared/system data is protected and counted once in the summary.
- Possible related paths appear in app details and in a separate list below either tab (hidden on Leftovers when Selectable only is on). These are suggestions with an explanation, not confirmed ownership. They cannot be selected or submitted for removal. Their bytes appear in each associated app's displayed Data size and Total size, with muted text showing the possible portion and the confirmed-only total. They do not affect App size, confirmed scanner totals, removal estimates, or data-last-changed dates. The summary counts each shared or possible related path once, even when associated with several apps; displayed app estimates can overlap when one path relates to multiple apps.
- Quit a running app before removing its bundle or data. Checks include NSWorkspace and bundle executables / surviving helpers; a process-check failure blocks removal. Known vendor uninstaller guidance is shown by bundle ID; bundle internals are not searched for uninstallers.
- Main accepts IDs, never renderer-supplied removal paths. Reviews expire after five minutes. A rescan invalidates old IDs/reviews. Identity, scope, bundle ownership, symlink ancestors/targets, and a recursive metadata fingerprint (native package manifest for bundles) are checked again before each Trash operation. Partial, shared, and system targets cannot be removed. If the bundle fails, all its selected data is skipped. Outcomes are reported individually and a new scan follows.
- Trashing does not immediately recover storage. Storage becomes available after Trash is emptied.

## Scan scope and limitations

Applications are discovered recursively in `/Applications`, `~/Applications`, and `/System/Applications`, stopping at `.app` bundles. System apps participate in ownership matching and remain protected. Each app is one opaque scan item: only its root `Contents/Info.plist` and Spotlight metadata are read for identity. Native macOS `du -s -A -k -P` (KiB converted to bytes) supplies the aggregate apparent size, and read-only `mtree -c -n -P` supplies a metadata fingerprint for removal revalidation. These native accounting passes must inspect package metadata to size it and detect internal changes, but do not follow links, discover candidates, or index embedded helpers. Internal package symlinks are ordinary package contents, not scan exclusions. Packages encountered inside Library data use the same boundary. Data candidates are only direct children of these user folders, measured recursively:

- `~/Library/Application Support`
- `~/Library/Caches`
- `~/Library/Preferences`
- `~/Library/Logs`
- `~/Library/Saved Application State`

Confirmed ownership uses exact bundle IDs (with `.plist` / `.savedState` suffix handling). There are no product-name or vendor alias tables. Previously audited name aliases such as `Code` now come from bundle metadata and are protected suggestions, just like all other name-based associations; only exact bundle-ID paths can be offered as removable app data.

The matcher derives protected relationships from:

- `CFBundleDisplayName`, `CFBundleName`, the `.app` filename, and distinctive product tokens in bundle IDs. Unicode normalization, camel-case/numeric word boundaries, punctuation/spacing normalization, and optional product roles (Desktop, Launcher, Client, Browser) adapt across devices. `+` is normalized to `Plus` so product editions retain their distinction.
- Full product names followed by a word/version/channel suffix, such as `Audio Hijack 27`. Exact normalized names win first, then the longest word-boundary prefix; `Code` does not match `Codec`.
- Product stems within the same reverse-domain namespace. For example, `com.microsoft.OneDriveStandaloneUpdater` relates to OneDrive, `com.autodesk.AutoCAD2024` can relate to installed AutoCAD, and `us.zoom.ZoomAutoUpdater` relates to an installed `zoom.us`. Multiword vendor prefixes can be removed from product names within that namespace, such as Raspberry Pi / Imager.
- A generic installer/updater/helper role under a single installed app's own brand namespace: `com.docker.install` relates to Docker because both the namespace and the installed app name identify Docker. Merely having one installed app from a vendor does not establish this product-level relationship.
- Vendor names, company-style suffixes (`BraveSoftware`), reverse/forward domains, and vendor-prefixed names/logs such as `Citrix Receiver` or `autodesk.webdeploy.streamer.log`. Namespaces are derived from installed bundle IDs and the direct-child candidate inventory. Thus a plain `Google` folder remains protected when reverse-domain Google preferences are present, even without an installed Google app; a named uninstalled product identifier remains unmatched.
- Alternate vendor namespaces supported by a complete distinctive product name in a scanned candidate. For example, the complete product name in `com.4kdownload.4K Video Downloader+` connects to the installed product metadata, allowing `4kdownload.com` to be shown as protected family data without an explicit vendor mapping. Candidate order does not affect this inference.
- A full installed app ID followed by a dot, or by an underscore for preference SQLite databases and their WAL/SHM sidecars. The longest matching ID wins.

Vendor-family context is always **shared**, even if only one family app is installed, and can include another or uninstalled product from that family. It does not claim that an uninstalled sibling product is installed. A more specific product stem takes precedence over a family association. Framework/default namespaces such as Electron, generic technical words, and Apple system namespaces cannot spread inferred ownership to unrelated products. A fully spelled distinctive product can still establish a protected suggestion under a runtime namespace without assigning other runtime apps to that product.

Every inferred association is protected and excluded from app totals/removal, regardless of candidate count. Shared paths are counted once. Missing bundle identities cannot produce app suggestions. Generic data/framework terms, macOS infrastructure, and company-name suffixes remain semantic protection rules, not product mappings. Without installed metadata or supporting namespace evidence, an unknown vendor/product name remains unmatched; there is no static catalog of uninstalled vendors.

Containers, Group Containers, `/Library`, launch agents, browser profiles elsewhere, and arbitrary disk locations are outside the scan. A possible leftover may belong to a CLI tool, helper, app installed elsewhere, or an app whose metadata could not be read. This is a conservative cleanup aid, not a complete uninstaller.

**Dates:** Last opened comes only from `mdls -raw -name kMDItemLastUsedDate`. Missing/unreadable Spotlight data is **Unknown**; no timestamp is substituted. Data last changed is the newest regular-file mtime observed recursively in matched app data, excluding top-level cache/log categories and recognized nested cache/log directories. Background processes can change data. Dates do not prove user activity, ownership, or that a file is safe to remove. Empty directories have no regular-file change date.

**Permissions:** macOS privacy controls and permissions can deny access. Skipped-location details and partial results remain visible; inaccessible bytes are not estimated. No permission elevation is requested by the app. Symlinks outside packages are skipped. Package accounting does not follow internal symlinks and does not report them as excluded locations. Directories changing during enumeration are marked partial. A scan is an observation over time, not an atomic filesystem snapshot.

**Storage:** Library sizes sum logical regular-file lengths, with hard links deduplicated within each measured item. Opaque package sizes use native apparent bytes, including internal directory and symlink metadata and native block rounding; packages are deduplicated independently. These estimates exclude resource forks and extended attributes. Compression, APFS clones, sparse allocation, purgeable storage, snapshots, and cross-item hard links can make these estimates differ from Finder, physical usage, or eventual recovered space. Shared candidate paths appear only once in the scan; they are excluded from each owner's displayed data/total columns. App size means bundle only; displayed Data size means confirmed external paths plus possible related paths; displayed Total size is bundle plus displayed data. The muted lines show the possible related contribution and the confirmed-only total.

**Races:** Conservative identity/fingerprint checks reject observed changes and symlink replacements. `shell.trashItem()` is a path-based OS API; it cannot provide an atomic validate-and-trash transaction against a hostile process replacing paths at the final instant. The app does not hash file contents or stop applications. It fails closed on observed changes and unavailable running-app checks; rescan if a selection changes.

All filesystem and OS operations stay in main behind a narrow, typed, context-isolated preload API. The renderer is sandboxed without Node integration. Navigation, new windows, permissions, webviews, and external network requests are blocked (only the local Vite origin is allowed during development). No telemetry, remote API, or automatic deletion is included.
